## P0-1｜抓娃娃机：真实键盘 Enter 不能触发抓取

### 实际代码情况

- `claw/Main.qml` 已监听主 Enter 和数字键盘 Enter，但有 `if (brainInput) return`：BCI 会话直接屏蔽本地键盘路径。
- 宿主事件路径 `onAction("confirm", true)` **只在 `brainInput` 为真时触发抓取**。注释解释它要防止来源不明的本地 `confirm`（可能由宿主保留的 Space 触发）错误抓取。
- `trigger()` 又要求 `canAlign` / 当前对准阶段。
- `claw/tests/verify_1106.py` 在 Linux Qt 模拟宿主中已通过 native `Qt.Key_Return` / `Qt.Key_Enter` 与五次操作测试；不能证明 Windows Neuralife 的实体按键转发链正常。

### 可能根因（待实机诊断，不能凭源码选一个）

A. 实际宿主吞掉原生 Enter，仅发一个不带按键来源的 `onAction(confirm)`；而当前本地确认被忽略 → 看似按键无效。
B. 用户在 BCI 运行状态尝试 Enter；`Keys.onPressed` 被主动屏蔽。
C. 真实窗口焦点在宿主菜单、其他控件或被抢走；`root.Keys` 没收到按键。
D. 用户实机加载的抓娃娃模块不是 V5 分支或不是预期打包产物。

### 修复任务

- 运行真实宿主的诊断构建，记录 `inputSource`、`activeFocus`、`phase`、收到的 `Qt.Key_Return / Qt.Key_Enter`、收到的 `onAction(confirm)`、`trigger()` 被门控原因。
- 找到 Enter 与 Space 在实际宿主中的不同事件流后，保证**主键盘 Enter、数字键盘 Enter、界面抓取按钮可以触发一次抓取；Space 不抓取；BCI 的 confirm 保持可用**。如果宿主只给不区分来源的 `confirm`，需要在输入适配层或宿主映射层解决来源问题，不能无差别放开 `confirm` 导致 Space 错触。
- `trigger(source)` 统一做阶段门控与防重复；按下后立刻转换阶段，使重复 host/native 事件不会二次抓取。
- 一次失焦再恢复，键盘继续有效；保留5次抓取、误差仅在结果后显示、近失误动画。

**验收**：Windows Neuralife 正常 Games 页打开，分别真实按 Return、数字键 Enter、Space、宿主确认按钮/模拟 BCI 确认；输出每次请求的来源、是否执行及原因；Enter 抓取 1 次、Space 抓取 0 次、同帧双路径只 1 次。不能以 Linux `QTest.keyClick()` PASS 替代。

### 当前代码和证据

    mode === "pursuit" ? "../pursuit/Main.qml" : "../target/Main.qml"),

## P0-3｜目标游戏黑边/没有填满画布

### 已发现的结构风险

- `pointer/Main.qml` 最外层是 `FocusScope`，未见像 `GameFrame` 中那样直接给套件外壳装 `LegacyWindowFill`。
- `childLoader` 的底部锚定在 `navigation.top`，而 `navigation` 运行中占 **52px 高度**：子游戏画布不会覆盖套件整个高度。
- 内部追光子游戏在 `GameFrame` 中有自己的 `LegacyWindowFill`；它适用于直接装到原宿主的场景，**嵌套在 pointer Loader 后不一定能识别到宿主固定比例缩放层**。
- `shared-ui/SceneViewport.qml` 按 1000×700 的 `min(width/1000,height/700)` 等比缩放，若被组合入口引入，会造成天然留边。

### 需要开发的修复

- 测量 `Window` 实际客户区、外层根 `FocusScope`、`Loader`、子游戏根、游戏场景的实际可见矩形（并记录`devicePixelRatio`）、`LegacyWindowFill.statusText`及日志；明确黑边来自哪一层，不能只把黑条涂成游戏背景色。
- **铺满适配应该归共同入口所有**；只对已确认的宿主 1000×700居中缩放约束解除，不修改未知父层。
- 若底部导航造成内容缺口，改为浮动按钮而不是永久占用52px的子游戏高度，并同步修复指针坐标变换；避免挤压导致追光球的目标位置跳动。
- 场景背景随可见窗口铺满；保留球体和容差圆的真实形状与场景相对尺寸，不通过非等比缩放拉伸圆球。

**验收**：1280×720、1512×982、1920×1080、2560×1440、3440×1440、3840×2160；至少 Windows 100/125/150% DPI真实窗口；最大化、还原、切换模式。全窗口无意外黑边/裁剪，九点坐标误差、准星命中仍≤2逻辑像素；如宿主不提供可安全解除的外层约束，记录阻塞点而不是强行篡改宿主。

## P0-4｜追光球：从5轮固定曲线改为3轮随机变速

当前 V5 `pursuit/Main.qml` **仍是5轮**：直线、椭圆、8字、自由、遮挡。自由轨迹 `buildSmoothAnchors` 围绕固定六组角点微扰、`generatedSmoothPathAt` 每段固定2.7/3.2秒且 `smoothstep` 在节点减速至0，具有明显循环规律。现有 `pointer/tests/verify_1106.py` 也把 `roundsCompleted=5` 写死。

建议3轮：

| 轮次 | 游戏行为 | 控制目标 |
|---|---|---|
| R1 基础自由追踪 | 随机平滑二维路径，低速、相对稳定 | 稳定持续跟随 |
| R2 变速自由追踪 | 随机路径，缓慢加减速，不在航点突然停下 | 实时速度适应 |
| R3 复杂自由追踪 | 更高曲率与速度变化、可选短时遮挡但不重置位置 | 修正与目标重捕获 |

**实现约束：** 使用固定seed的随机航点与速度计划，先生成全部轨迹/速度关键帧，保存 `pathSeed`、`waypoints`、`speedSchedule`、轮次参数。推荐 Catmull-Rom 或连续速度的样条 + 弧长参数化，沿路径距离由速度积分控制；速度/加速度限幅，边界留出容差圈。不要每帧随机重采样目标，不能瞬移、频繁掉头或规律性停顿。

**验收**：3轮各25秒或经配置时长；相同seed同时间采样轨迹相同，不同seed改变轨迹；L2/L3能出现真实不等速且速度曲线连续，基础关无过快运动；暂停不推进位置，遮挡段另记误差。`pointer/tests/verify_1106.py`、`pursuit/TaskDefinition.qml`、两套自动场景、总结结果一起改为3轮。

## P1-1｜四向律动：3轮教学 + 标签与方向框留白

### 已确认源码问题

`rhythm/RhythmEngine.js` 仍写死5个 `roundNames` 和 `roundHelp`，用 `r===3` 生成长音、`r===4` 变速，且 `endRound()` 只有 `s.round===4` 才结束；不能只改标题。用户新要求三轮：**四方向键位教学 / 长音符保持教学 / 普通与长音符混合训练**。

截图中方向标签和判定箭头很近，V5 `rhythm/Main.qml` 中 `board.lineY=84` 固定，而 `board.notePx` 随大屏可放大到96px：判定框顶端为 `84-96/2=36`；标签固定 `y=12`，字高增大后可能几乎贴上或重叠。这是可以从代码直接确认的结构原因。

### 具体修改

1. 全部3轮，轮1每个方向至少2个音符，轮2四个方向长按各出现，轮3混合短音+长音且均衡随机。3种难度仍然控制BPM、提示提前量和判定窗，不再作为额外轮次；若脑机硬件只有两分类，不得将四方向键盘提示写成“四类运动想象解码已验证”。
2. `rhythm/RhythmEngine.js` 修改 `roundNames/roundHelp/chart/endRound/summary` 的固定轮数和指标分母；`rhythm/Main.qml` 修改“第x/5轮”、进度条 `model:5`、结果页“五轮”、间歇提示；`TaskDefinition.qml/README`、Node/Qt测试同步。
3. 标签与框必须采用相关定位：`markerTop = board.lineY-board.notePx/2`，`labelBottom = markerTop-labelGap`，建议 `labelGap>=20px`，标签 `y=labelBottom-label.implicitHeight`。相应地将 `lineY` 动态提高到满足标签高度的最小值（不能继续固定84）。同时保持轨道中心线、长尾与音符y统一引用判定线。
4. 当前长尾按结束剩余时间缩短的机制已存在，**不能因缩减轮次回退**；音乐、节拍、音效的准备页及局中开关都保留。
5. 在截图同样大小的窗口和1920×1080、2560×1440、3440×1440下，测试标签与图标最小视觉间距、四轨和右侧文本不溢出/遮挡。

参考约束（数值需要在真实截图下确认）：

```qml
readonly property real markerSize: board.notePx
readonly property real labelGap: Math.max(20, Math.min(30, board.height * 0.03))
readonly property real requiredTop: markerSize/2 + labelGap + root.captionPx + 18
readonly property real lineY: Math.max(requiredTop, Math.min(160, board.height * 0.16))
// 标签 y = (lineY - markerSize/2) - labelGap - label.implicitHeight
// 判定框 y = lineY - markerSize/2
```

**验收**：3次 `round_started`、3次 `round_completed`、一次 `session_completed`，不会在第二轮错误结算；任意窗口标签/方框间距达标，长尾实时缩短并在结束时归零。

## P1-2｜鲁班锁：五关已存在，但关卡深度仍不足

### 不应误判“完全没做”

V5 `luban/LevelData.js` 已有L1–L5，L4名为“偏移双槽·往返解锁”，L4/L5有中途滑移；`luban/tests/evidence/runtime-result.json` 能找到 `mouse_L4_no_initial_whole_piece_move`、`axis_arrow_partial_drag`、`continuous_no_penetration` 等 PASS。说明目前的几何互锁机制**在模拟测试里有实现**。但用户认为仍像简单嵌合，说明需要提升**可视的因果链和实际谜题难度**，不能只在技术报告里用“有碰撞”代替游戏设计。

### 改法

- L1/L2仅教学；L3不应再标`kind:"teaching"`，重新设计为必须观察遮挡、判断钥匙件和方向的小谜题；不自动选择正确部件。
- L4/L5保留连续滑移和几何验证，并增加明确的**中间状态**：第一次只能滑一段、需要移动另一木件/反向调整后才可继续拆出；至少一个看似可动的选择是受阻的。避免顺序一眼就能猜中。
- 关卡难度不能只数木件数：提供最短/参考动作步骤、关键中间状态数、可选动作数、错误方向可恢复性、首次可完全抽出部件数、求解器是否找到逆向复位路径。
- 鼠标左键拖动场景自然旋转，单击选择件，独立的方向操作柄负责滑移；已有手势保留，减少直接标出正确解锁顺序的提示。允许分层提示：先提示观察区，再提示阻挡结构，最后才提示关键部件。
- 参考 https://github.com/YoungJett123/luban-lock-studio 的连续拆解与几何检查思想，不复制第三方模型或代码。保留原生 Qt Quick 3D；L3–L5必须提交完整拆解及复位视频或可复现状态动作记录。

**验收**：至少L3、L4或L5具有无法简单直线逐根抽出的复杂锁定；推回/撤销/旋转不穿模，锁定前后的可行方向有明确变化；有人实际试玩并反馈可以理解为何受阻，不能只靠solver PASS。
